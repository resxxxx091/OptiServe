# 订单与客诉场景处理矩阵

订单客诉附表，配合 `SKILL.md` 使用。只在需要确认某场景能说到哪一步、是否必然人工时读取。

**本表不给任何时效数值。** 审核时长、到账天数、赔付比例一律不写进表，对运营一律用"以平台实际处理为准"。

## 场景 × 已知信息 × 处理边界

| 场景 | 必须先核验的信息 | 现在就能说明的 | 是否必然人工 |
| --- | --- | --- | --- |
| 退款金额不符 | 订单号、实付金额、申请金额、优惠使用情况 | 审核要素是否齐全；差异可能来源（券/运费/部分退） | 是，金额不由系统承诺 |
| 支付成功订单未生成 | 扣款时间、支付渠道、订单列表截图摘要 | 核对路径；可能原因（延迟/风控拦截） | 是，要查支付流水 |
| 已揽收改地址 | 订单号、新旧地址、物流单号 | 拦截成功与否不确定；新旧地址都要留 | 是，要联系物流 |
| 客诉多次催办未解决 | 工单号、首次投诉时间、已承诺过的处理 | 升级路径；升级后会有专人跟进 | 是，升级即转人工 |
| 疑似恶意退货 | 订单号、历史退货记录 | 只陈述数据事实，不下结论 | 是，由平台规则团队判断 |
| 发货超时客诉 | 订单号、承诺发货时间、实际发货时间 | 赔付规则以平台规则页为准；先安抚 | 视情况，涉及赔付必然 |
| 系统报错 | 错误码、时间、影响范围、复现步骤 | 初步排查清单；收集信息 | 查日志/数据库必然 |

## 信息索取边界

- 可以索取：订单号、物流单号、问题发生时间、脱敏后的截图摘要、错误码。
- 禁止索取：买家或运营的支付密码、短信验证码、完整银行卡号、身份证照片。
- 任何一方贴出凭证时，提醒不要在公开渠道留全量信息。

## 措辞替换

| 不能说 | 可以说 |
| --- | --- |
| 退款已经通过 | 退款申请已受理，审核结果以人工核验为准 |
| X 个工作日内到账 | 具体到账时间以支付渠道实际处理为准 |
| 这单是恶意退货 | 历史退货记录为 N 次，是否异常由人工判断 |
| 系统问题我们已经修复 | 故障已登记，修复进展以技术团队通报为准 |
