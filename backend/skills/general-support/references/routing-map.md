# 分流与转接对照表

通用运营接待附表，配合 `SKILL.md` 使用。只在拿不准该转哪一路、或转接前不知道该总结哪些字段时读取。

本表只回答"交给谁、带什么信息"。表中任何一路都不表示问题已经处理完成——分流不等于处理，转接动作要说成"建议转…"或"已为你登记"，不能替下游角色声称结果。

## 现象 → 去向

| 用户描述 | 去向 | 转接前需要拿到或总结的字段 | 这一路不能做的事 |
| --- | --- | --- | --- |
| 登录失败、页面报错、接口或 SDK 异常、App 崩溃、配置失败、数据不同步 | 技术支持 | 现象是否持续复现、报错信息或截图、使用环境（浏览器/App/服务端）、最近有没有改版或改配置 | 不猜根因，不编造服务状态 |
| 扣款、退款、发票、账单、订阅续费、优惠券抵扣、支付状态 | 账单支持 | 订单号或交易号、支付时间与渠道、金额与币种、用户期望的处理结果 | 不承诺退款成功、到账时间、账单调整结果 |
| 订单状态、发货进度、配送时效、收货信息变更 | 订单支持 | 订单号（优先）、下单时间、收货手机号后四位 | 不承诺具体到货时间，不声称已改地址或已取消 |
| 账户类问题（登录方式、账号异常、资料修改） | 先澄清再分流：偏技术走技术支持，偏权限审批走人工 | 登录方式、账号标识、问题发生时间 | 不要密码、验证码、支付密码、完整银行卡号、身份证照片 |
| 售后类（退换、维修、补偿诉求） | 按争议内容分流：涉及金额转账单支持，涉及状态转订单支持 | 购买渠道、问题描述、期望处理方式 | 不承诺补偿结果 |
| 投诉、建议、服务不满 | 先承认体验问题，情绪激烈或要求升级时转人工 | 事件发生时间、涉及订单或服务、用户期望的解决方案 | 不和用户争辩，不套用冷漠模板 |
| 明确要求人工、涉及权限审批、法律或监管表述 | 人工 | 已完成的信息收集与仍未闭合的点 | 不再重复索要用户已经给过的字段 |
| 同一句里混了技术和账单（或订单）两类问题 | 不合并处理：先拆分，说明会分别处理，再逐条分流 | 每条问题各自的关键字段 | 不要用一个答案糊过去 |

## 转人工前的总结四件套

1. 用户诉求一句话。
2. 已知事实：用户已经提供的订单号、时间、渠道、报错原文等，列出来避免重复询问。
3. 仍缺什么：只列真正阻塞判断的字段。
4. 为什么要人工：命中上表哪一行，或涉及哪类权限/资金/隐私核验。

## 措辞替换

| 不能说 | 可以说 |
| --- | --- |
| 马上到账 / 一定成功 / 百分百解决 | 需要核验后才能确认 |
| 我已查到，订单已经处理 | 我这边没有系统查询结果，先说明当前能判断的范围 |
| 请自行查看规则 / 这是系统规定无法处理 | 这项规则是…；如果你的情况属于…，我可以转人工继续看 |
| 已经帮你转好了，稍等就会有结果 | 已登记你的诉求并转人工，仍需人工核验——且只有真正拿到受理回执后才能这样表述 |
